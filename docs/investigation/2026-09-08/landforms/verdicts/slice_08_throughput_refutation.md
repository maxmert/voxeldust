# Slice 8 — THE THROUGHPUT WORK (M8-2a, ruling V15): the refutation

The refuter read the whole uncommitted diff against `73a9758`. The step-4 findings stay in
`slice_08_step4_refutation.md`; this file holds the throughput work only — the priority queue, the
parent cache's claim, the request order, the counters, the gate's prints and the docs.

**Example, in the game's words.** A hull flies over the home planet at 528 m/s. The eye sweeps a new
ring of ground every second. The workers build that ring's chunks, and each chunk reads eight parent
meshes from one cache. This work orders the jobs, sizes the cache, and builds each parent once. The
findings below say where the order, the cache and the numbers break.

## What the refuter tried to refute and could NOT

1. **A nested claim cannot deadlock two workers.** `get` claims, builds and finishes one parent
   before it returns (`chunks.rs:434-440`), and `geometry_with` reads its eight parents one after
   another (`chunks.rs:638-641`). A worker therefore holds one claim at a time, so no two workers can
   wait on each other.
2. **The claim loses no wake-up.** `finish` changes `building` and `map` under the lock, and it
   notifies after it releases the lock (`chunks.rs:481-492`). A waiter re-reads both under the lock
   inside its loop (`chunks.rs:449-465`), so an early notification is not lost.
3. **`Drop` cannot deadlock.** It takes the queue lock, sets `closed`, and notifies
   (`terrain.rs:227-235`). A worker holds that lock only between a pop and a wait.
4. **The close loses no job.** A worker pops before it tests `closed` (`terrain.rs:174-186`), so the
   queue drains before the threads leave.
5. **The arrival order is stable.** `seq` rises under the lock immediately before the insert
   (`terrain.rs:253-257`), and a `u64` does not wrap in a session. Two jobs of equal priority keep
   their submission order.
6. **The ground still fills coarse first, with no hole.** The urgent territories tile the drawn
   ground: `inside = (geo.near < switch_m(col.rung)) & (geo.far > fade_in[1])`
   (`ladder_view.rs:609`), and a rung's `fade_in[1]` is `HYSTERESIS_OUT * switch_m(rung - 1)`
   (`ladder_view.rs:94`). For any distance exactly one rung claims the ground, and within the urgent
   class the coarser rung goes first. The margin class is the crossfade PARTNER, not the cover.
   *A caveat, not a refutation:* the partner now builds last, so at boot a band's crossfade runs
   one-sided until the whole urgent class lands. The picture is coarser there, never empty.
7. **The release hold does not read the key order.** `overlapping_missing` walks `index`, a
   `BTreeMap` by face and rung (`ladder_view.rs:431-447`), so the reordering cannot break it.
8. **`morton` does not overflow.** Thirty-two bits of each axis interleave into sixty-four, and the
   test pins `morton(i32::MAX, i32::MAX) == (1u64 << 62) - 1` (`ladder_view.rs:1144`).
9. **`depth = rungs - key.rung` cannot underflow.** `descend` emits `col.rung` in `0..rungs` only
   (`ladder_view.rs:589-597`).
10. **`Face` is orderable.** `crates/seed/src/bend.rs:76-86` derives `Ord`, so `RequestOrder`'s derive
    groups the parents by face as its comment claims.
11. **A taken-and-skipped job leaves no marker behind.** The worker REMOVES the entry instead of
    reading it (`terrain.rs:193-197`), so the `cancelled` set does not grow for a job a worker
    reaches. It grows only for a job no worker ever reaches — that is T-3.
12. **The 225 MB is registered, and the missing byte budget is disclosed.** `DEFERRED` D-TERRAIN-5
    item 11 carries the memory with its step. Item 9 and §16.6 both state that V15's byte budget lands
    with step 5's packing. Neither hides.
