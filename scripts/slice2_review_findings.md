**Cloud preflight validates only VD_STORE_DURABLE_ROOT; the M3 durable boot-counter uses VD_BOOT_DURABLE_ROOT/VD_BOOT_STATE_DIR, so the split-brain incarnation counter can live on an ephemeral k8s emptyDir under cloud (fail-open)**

- claim: enforce_cloud_preflight only requires + temp-checks ONE durable root: `let root = env.string("VD_STORE_DURABLE_ROOT")...ok_or(MissingDurableRoot)?; if is_under_temp(&canon_lenient(Path::new(&root))) { return Err(DurableRootUnderTemp...) }`. But the M3 durable monotone boot-counter — the single most safety-critical durable action, whose whole purpose is to stop a restarted node re-using an incarnation and having its traffic silently deduped (the R-6a/M3 split-brain invariant) — is written by resolve_process_incarnation via `check_durable_path(&path, VD_BOOT_DURABLE_ROOT, ephemeral)` using the SEPARATE key VD_BOOT_DURABLE_ROOT (lib.rs:278), which the preflight NEVER requires or validates. When VD_BOOT_DURABLE_ROOT is absent (the normal cloud config — the new positive-control test sets VD_BOOT_STATE_DIR but no VD_BOOT_DURABLE_ROOT), check_durable_path takes the `None` deny-list branch (boot.rs:174) and only rejects a path under /tmp. The code's OWN documented threat model (boot.rs:125, lib.rs:299) states a k8s `emptyDir` mounts under `/var/lib/kubelet/...` (NOT /tmp) so the prefix DENY-list cannot catch it — which is precisely why cloud force-enables the allow-list for the store. That allow-list is never enforced for the boot-counter, so cloud accepts an ephemeral emptyDir boot-state dir. The preflight also forbids VD_PROCESS_INCARNATION and VD_BOOT_STATE_EPHEMERAL_OK, making the durable-counter path mandatory — which makes this the ONLY incarnation source in cloud, so its non-durability is the fail-open, not a footnote.
- fix: In enforce_cloud_preflight, when Profile::Cloud, also require the boot-state durable root: if VD_BOOT_STATE_DIR is set (or unconditionally, since the counter path is mandatory in cloud), require VD_BOOT_DURABLE_ROOT to be present, non-empty, and NOT under-temp — the same MissingDurableRoot / DurableRootUnderTemp treatment given to VD_STORE_DURABLE_ROOT — so the boot-counter runs check_durable_path in allow-list mode (catching an emptyDir the deny-list cannot). Equivalently, unify the store and boot-state durable roots under one cloud-required key, or thread the cloud flag into check_durable_path so its None-branch is forbidden in cloud.
