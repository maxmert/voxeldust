# Reusable OSS engines/servers for Voxeldust — deep research (2026-07-05, run wf_7a2e1d74-29f)

## Bottom line

Surveying the prior platform-survey's actual gap — open-source voxel engines and game servers — yields no new adoptable Rust dependency for Voxeldust: every candidate is blocked by language (C++/C#/Unity/JVM), license (GPL/LGPL/unlicensed), or death, so all fall into study-patterns-only or reject. The most actionable reuse opportunities are architectural references, ranked: (1) MultiPaper's Master-mediated chunk-ownership handoff + subscription cache sync is the closest Minecraft-ecosystem analogue to cross-shard entity transfer; (2) Veloren's Rust codebase — an embeddable `server` library crate and an isolated `world` worldgen crate — is the best Rust server-architecture and voxel-worldgen reference (GPL-3.0, flat finite worlds, so reference-only); (3) Folia's strict per-region data isolation is an in-process (threads-not-processes) analogue of sealed shards, and its enumerated API breakage is a cautionary map of cross-boundary costs; (4) godot_voxel documents an SDF-based spherical-planet workflow (MIT but C++/Godot-coupled); (5) Seed of Andromeda is the only permissively-licensed (MIT) spherical-planet voxel code that could legally be ported, but it is C++ and dead since 2021. Critically, no engine exists that is simultaneously spherical-planet-capable, Rust, permissively licensed, AND maintained: the Rust spherical-planet candidate (Voxanet) is unlicensed and dormant, the MIT spherical-planet candidate (SoA) is dead C++, and the maintained voxel engines (Luanti, godot_voxel) are C++ with no spherical-planet-first design. This confirms and does not overturn the prior survey's implicit conclusion that Voxeldust's spherical-voxel + sealed-shard core must remain greenfield.

## 1. Veloren is the strongest Rust reference for Voxeldust's server architecture and voxel worldgen — but GPL-3.0 and flat finite worlds make it reference/study-patterns-only, not adoptable code.
*Confidence: high · verification: 3-0 unanimous across 5 merged claims*

Veloren packages its core server logic as a standalone embeddable Rust library crate `veloren-server` (a `Server` struct with new()/tick()/cleanup(), no [[bin]] target), consumed separately by the `server-cli` frontend and by Voxygen's singleplayer — so the server can be studied/embedded independently of any frontend. Worldgen is isolated in its own `veloren_world` crate explicitly 'intended to allow viewing, generating, and simulating a Veloren world without a client or server,' with a standalone map-generator example. A complete open dedicated-server implementation ships with the project (self-hostable via `cargo build --bin veloren-server-cli`, docker-compose, even Raspberry Pi) and source is public with outside contribution invited. Two constraints on REUSE: (a) the whole project is GPL-3.0, so code can be read/referenced but not lifted into Voxeldust without imposing copyleft — reference-only is the correct and only license-compatible mode; (b) Veloren generates flat finite worlds, not spherical planets, so its worldgen ALGORITHMS have limited direct applicability. Maintenance signal is mixed but repo is live: the official devblog stalled ~7.5 months (latest 'These weeks in Veloren 250' dated 21 Nov 2025, roughly quarterly before that), yet the GitLab repo was pushed the same day as verification (2026-07-05) — public communication cadence slowed, the codebase itself remains active. Verdict: study-patterns-only (Rust server-crate structure, ECS, persistence, isolated worldgen crate).

Sources: https://book.veloren.net/contributors/developers/codebase-structure.html · https://gitlab.com/veloren/veloren · https://veloren.net/ · https://veloren.net/blog · https://book.veloren.net/players/server-hosting/introduction.html

## 2. MultiPaper is the closest Minecraft-ecosystem analogue to Voxeldust's cross-shard entity-transfer problem: distributed authority over one shared world via a central Master plus chunk-ownership handoff and subscription-based cache sync.
*Confidence: high · verification: 3-0 unanimous across 2 merged claims*

MultiPaper scales a single Minecraft world across multiple coordinating server processes. A central MultiPaper-Master stores the world files/data, coordinates the servers, and 'Decides who gets to tick the chunk (first in first served basis).' The handoff mechanism is directly analogous to cross-shard transfer: a server wanting to tick an unowned chunk must first request ownership from the Master ('it won't [tick], but will instead send a request to the Master to take ownership of it'); if denied, it keeps the chunk in sync with the owner. Cache coherence is subscription-based: 'When a server has a chunk loaded into memory, it will subscribe to any changes made within that chunk,' so a block change on the owner propagates to all subscribers. This solves authority handoff at CHUNK (not entity) granularity via a CENTRAL-MASTER model — the claim honestly flags this differs from Voxeldust's sealed-shard directory-CAS model (no central data store; shards are private). It is the one true cross-process authority-handoff design in the MC ecosystem (Folia is single-machine threading; hyperion/valence are single-server). Constraints: JVM/Java (Paper fork), so reference-only for a Rust workspace. Verdict: study-patterns-only — the highest-value reference for the cross-shard transfer + directory-ownership pattern.

Sources: https://github.com/MultiPaper/MultiPaper · https://multipaper.io · https://deepwiki.com/MultiPaper/MultiPaper

## 3. Folia is an in-process (threads, not distributed processes) analogue of Voxeldust's sealed-shard ownership model, and its enumerated API breakage is a candid map of the real cost of cross-boundary operations — which Folia does NOT solve seamlessly.
*Confidence: high · verification: 3-0 unanimous across 3 merged claims*

Folia groups nearby loaded chunks into 'independent regions,' each with its own tick loop at 20 TPS, executed in parallel on a thread pool — 'There is no main thread anymore.' It enforces strict region data isolation: 'Code that is running in one region under no circumstance can be accessing or modifying data that is in another region,' and 'The only guarantee of thread-safety comes from the fact that a single region owns data in certain chunks.' This is a sound in-process analogue of sealed-shard exclusive ownership — but achieved by discipline within a shared address space (thread-check APIs, corruption warnings, dynamic region merge/split), not the hard process/redb boundaries Voxeldust uses. Crucially for Voxeldust's transfer problem, Folia demonstrates the COST rather than a solution: regionization breaks portals, respawning, ALL scoreboard API, world loading/unloading, and Entity#teleport ('This will NEVER UNDER ANY CIRCUMSTANCE come back, use teleportAsync'), and only plugins explicitly marked `folia-supported: true` load. Cross-region entity movement is precisely what breaks the synchronous API — the direct analogue of cross-shard entity transfer, and Folia offloads it to async schedulers rather than solving it seamlessly. Constraint: JVM/Java, reference-only. Verdict: study-patterns-only (region isolation discipline + a cautionary catalogue of what cross-boundary operations break).

Sources: https://github.com/papermc/folia · https://deepwiki.com/PaperMC/Folia · https://docs.papermc.io

## 4. godot_voxel is a maintained MIT C++ Godot-4 module with a rare officially-documented spherical-planet (SDF) workflow, but its multiplayer is experimental/partial and it ships no server — reference-only for Voxeldust.
*Confidence: high · verification: 3-0 unanimous across 3 merged claims*

Zylann/godot_voxel is MIT-licensed, 93% C++, actively maintained (latest release v1.6 'Godot 4.6 + Voxel Tools 1.6' dated 2026-02-04, ~4,961 commits, 3.8k stars, pushed 2026-07-02). It is a Godot-4 C++ module/GDExtension — not a standalone engine or server. It is one of the very few maintained voxel engines with ANY documented spherical-planet workflow: the official VoxelGeneratorGraph docs walk through building a planet from an `SdfSphere` node ('A good way to begin a planet is to make a sphere with the SdfSphere node'), with dedicated SdfSphereHeightmap/Normalize nodes — but this is SDF generation within the standard cubic grid, NOT a dedicated spherical-planet coordinate system. Multiplayer is explicitly experimental and partial: a server-authoritative VoxelTerrainMultiplayerSynchronizer exists for blocky VoxelTerrain via Godot's high-level RPC ('very experimental and might change'), but LOD terrain (VoxelLodTerrain) has 'no support for now' — a limitation unchanged through v1.4/v1.5/v1.6. No distributed/shard/MMO server layer exists. Constraints for Voxeldust: C++/Godot-coupled (cannot link into a pure-Rust sealed-shard workspace), no server process, and its only networking is single-process Godot RPC replication. Verdict: reference-only — read its SDF planet generation, meshing, streaming, and LOD code.

Sources: https://github.com/Zylann/godot_voxel · https://voxel-tools.readthedocs.io/en/latest/generators/ · https://voxel-tools.readthedocs.io/en/latest/multiplayer/

## 5. Seed of Andromeda (SoACode-Public) is the only permissively-licensed (MIT) spherical-planet voxel code that could legally be reused or ported — but it is 90.8% C++ and effectively dead since June 2021.
*Confidence: high · verification: 3-0 unanimous across 3 merged claims*

RegrowthStudios/SoACode-Public carries a genuine, unmodified MIT license (verified in raw LICENSE.txt, not just an SPDX guess), and its engine-framework dependency Vorb is also MIT — so its spherical-planet voxel code could legally be read, reused, or ported (subject only to MIT attribution for lifted portions). This is the key differentiator versus Voxanet and Planetcraft, which are unlicensed. However: the codebase is 90.8% C++ (Python/CMake/Objective-C fragments), so it cannot be a Cargo dependency — any reuse means FFI-wrapping or reimplementation, i.e. reference/port-only for a pure-Rust greenfield. And it is dead: last push 2021-06-05 (over five years stale; last commit on default branch older still, 2020-03-02), archived:false but no post-2021 branch activity — there is no maintained Seed-of-Andromeda successor in this repo. Verdict: reference/port-only — the single legally-liftable source of spherical-planet voxel algorithms, valuable as an algorithm reference despite being unmaintained C++.

Sources: https://github.com/RegrowthStudios/SoACode-Public · https://github.com/RegrowthStudios/Vorb

## 6. Luanti (ex-Minetest) is a mature, actively-maintained C++/Lua voxel engine+server, but LGPL-2.1 copyleft and its C++ monolithic architecture make it reference-only for Voxeldust.
*Confidence: high · verification: 3-0 unanimous across 3 merged claims*

Luanti is the most mature open voxel engine surveyed — 80.7% C++ engine core with Lua (~9.6%) scripting, actively maintained (latest release 5.16.1 dated 2026-05-10, 13.2k stars, 13,543 commits, same-day push activity). Its code is LGPL-2.1-or-later: dynamic linking is permitted without copyleft on the linking app (subject to LGPL relink/notice terms), but any statically vendored/modified engine code stays LGPL with source-sharing obligations (media is CC BY-SA). For Voxeldust the binding blockers are structural, not just licensing: it is a monolithic C++ application with no embeddable library API and an Irrlicht-derived MULTITHREADED renderer, incompatible with the project's 100% llvm-cov region+branch coverage rule (foreign C++ can't be instrumented), the clippy-enforced sim::io seam, and the deterministic single-threaded per-shard sim. There is zero Rust in mainline (the 2019 gradual-Rust-rewrite proposal never landed). Nit: 'cannot be linked' is technically overstated (cxx/bindgen could bind C++), but it is not practically or contractually adoptable given the hard constraints. Luanti also documents NO spherical-planet workflow. Verdict: study-patterns/reference-only (mature modding API, chunk streaming, and long-lived server operation as reading material).

Sources: https://github.com/luanti-org/luanti · https://docs.luanti.org/for-creators/licensing

## 7. Voxanet is a rare Rust/wgpu spherical-planet voxel engine but is UNLICENSED (all-rights-reserved) and a dormant 4-day micro-demo — reject for reuse, at most read-only conceptual reference with clean-room risk.
*Confidence: high · verification: 3-0 unanimous across 3 merged claims (feature-existence evidence medium/self-reported; license+maintenance facts high)*

verlorengest/voxanet is the only Rust/wgpu spherical-planet voxel engine surfaced: it self-describes generating spherical terrain via Nowell's cube-to-sphere mapping, a custom spherical-gravity physics engine (Up vector from position relative to planet center), and quaternion-based character orientation on curved surfaces — architecturally the closest match to Voxeldust's core, and in the right language. But two facts make it a reject for reuse: (1) NO open-source license — GitHub API reports license:null AND the repo root has no LICENSE/COPYING file, so it is genuinely all-rights-reserved; GitHub ToS grants only view/fork, not reuse/modify/redistribute, so it cannot legally be used wholesale or partially, and even conceptual reference carries clean-room risk. (2) It is a dormant micro-project, not a maintained engine: created 2026-01-08, last pushed 2026-01-12 (9 commits, ~4 days of activity), 10 stars, 1 fork, then ~6 months of silence — a self-described technical demo with no code-level audit that the features fully work (feature claims are README self-description, medium confidence). Verdict: reject for adoption; conceptual read-only reference only, and only if clean-room-safe.

Sources: https://github.com/verlorengest/voxanet · https://choosealicense.com/no-permission/

## 8. Planetcraft is an unlicensed, dead Unity3D/C# proof-of-concept of Minecraft-like voxels on a spherical planet — technique reference only, not adoptable.
*Confidence: high · verification: 3-0 unanimous across 3 merged claims*

ddupont808/planetcraft is a Unity3D/C# (59% C#, plus JS modding API/GLSL/HLSL) playable proof-of-concept of a Minecraft-like voxel game 'mapped onto a large-scale spherical planet' (12km voxel planet, flood-fill lighting with AO) — not an engine or server, and no multiplayer. It is doubly blocked for reuse: (1) NO license (GitHub API license:null, no LICENSE file, no reuse grant in README), so all-rights-reserved by default — reference-only for the ideas at most; (2) effectively dead — created and last pushed the same day, 2024-01-07, only 2 commits, 11 stars, ~2.5 years stale. Cross-language Unity/C# POC code cannot be adopted into a Rust workspace regardless. Verdict: reject for adoption; the only reusable element is the spherical-voxel 6-grid/cube-sphere mapping technique as a concept reference.

Sources: https://github.com/ddupont808/planetcraft
